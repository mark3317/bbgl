# BBGL / BBSC-GL: разработка и проверка

Пути относительно корня текущего checkout, а Markdown-ссылки — относительно
этого файла. Подготовка другой машины: [WORKSTATION.md](../../../docs/WORKSTATION.md).
Путь установки и MSYS2 определять на текущем устройстве; примеры старых
машин в исторических документах не использовать как defaults.

## Цикличные обработки — только с разрешения пользователя, 06.11.2026

Любые новые цикличные обработки в моде (периодические опросы, таймеры,
ticks, фоновые проверки и повторы), в том числе внутри существующего
обработчика, добавлять только после явного разрешения пользователя
на конкретный механизм. Общая просьба исправить баг или добавить функцию
не считается таким разрешением. Обоснованная невозможность штатного решения
тоже не заменяет разрешения. До согласования описать назначение, период,
объём работы и ожидаемую стоимость; сначала искать штатный событийный путь.
Такие обработки не должны ухудшать общую оптимизацию: оценивать суммарную
нагрузку, включая простой и рост числа игроков/объектов, и проверять влияние
на производительность. При обнаружении регрессии устранить её до принятия
изменения; одно разрешение на механизм не означает согласия на ухудшение.

## Приоритет штатной реализации — 06.11.2026

При любых изменениях и новых доработках BBGL/BBSC сначала искать и пробовать
использовать или корректировать штатные условия и обработки игры/порта.
Снятие конкретной штатной блокировки предпочтительнее нового обработчика,
опроса, сканера, очереди, сетевого сообщения или повтора. Новый механизм
добавлять только при обоснованной невозможности штатного решения;
объяснить ограничение и стоимость, сохранить native control flow и авторитет.
Это не расширяет запрос сборки/логов до самостоятельной правки кода.
Перед изменением поведения/оптимизацией читать
[накопленные знания](../../../mods-src/BBSC/docs/OPTIMIZATION.md).


Для повторяющихся операций «собери/обнови на ПК» и «готово, собери
последние логи» использовать отдельный
[bb-coop-build-deploy-logs](../bb-coop-build-deploy-logs/SKILL.md):
там готовые скрипты быстрой установки с бэкапом и сбора ротированных логов
с фактическими BB_USER_DIR. Этот навык остаётся для анализа и исправления кода.

Указание от 03.11.2026: полный цикл сборки/установки/запуска выполняется через
bb-coop-build-deploy-logs после завершения связанных доработок во всех параллельных
чатах. Доступны ПК + ноутбук для сети и три экземпляра на ПК для логики мода.
Это разрешено и для обычных доработок, не только эксперимента serverless-party.
По запросу запуска агент запускает игру сам; прежние ограничения ниже «обычный
деплой только ПК» и «не запускать игру за пользователя» заменены этим указанием.

Общаться по-русски. Цель — устойчивое прохождение в коопе; объединять связанные
исправления в один осмысленный игровой прогон. Код, сборка, деплой и подтверждение
пользователем — отдельные статусы. Не объявлять баг закрытым только по fixture-тесту.

## Быстрый деплой — указание пользователя от 02.11.2026

По указанию от 03.11.2026 лёгкие клиенты эксперимента serverless-party
тестируем на этом ПК, игру — на ПК и ноутбуке в отдельных тестовых установках.
ПК + ноутбук разрешены также для обычных доработок по указанию от 03.11.2026.
Bloodborne Player 1/2/3.exe из общей установки используют отдельные
%LOCALAPPDATA%/Bloodborne Game Launcher Player 1/2/3 (три папки с полным префиксом),
BBGL_PROFILE_DIR и BB_P2P_PORT 3658/3659/3660. Роли определять по прогону;
кооп-аккаунты у клиентов разные. Логи собирать со всех участвовавших профилей.

Для обычной сборки/установки приоритет у обновлённого bb-coop-build-deploy-logs:
без проверок файлов, SHA256, verify-release и сверки manifest. Для DLL — delta,
не пересборка всего пакета. Старые требования verification ниже относятся к
прежнему процессу. Сохранять бэкап, данные и запрет замены при работающей игре.
Целевые проверки изменённой логики в разработке остаются; ради деплоя не повторять.

## Архитектура после перехода на Party — 04.11.2026

Основной кооп запускает Party внутри run.py; VPS и отдельный gameserver не нужны.
launcher/bbport_party.py отвечает за discovery/mesh и конфигурацию; mods-src/BBSC/party
— за согласование группы и loopback-совместимость native NP/HTTP. Native gameplay
идёт по UDP. Названия shadNet/relay в native коде не доказывают неиспользуемость:
проверять вызовы и сборку. Не удалять серверный исходник только по отсутствию в ZIP.
Релизные подробные логи выключены; отсутствие события в них не доказывает отсутствие
игрового действия. Актуальные открытые баги брать из HANDOFF, не из старого study.
UI-тестам нужен out/qt-venv/Scripts/python.exe; обычный python может не иметь PySide6.
Каталог тестов: docs/TEST-CATALOG.md родительского проекта. Часть unittest-файлов
не вызывает unittest.main(): запускать конкретный модуль через unittest, иначе
прямой python file.py может завершиться без единой проверки. Native harness могут
выполняться при импорте, VPS/Blender/ELF-скрипты — ручные; общий discover не запускать.
Устаревшие save/profile contracts сохранены с явным skip, не считать их PASS.

## Источники и среда

- Локальный Windows/PowerShell, MSYS2 CLANG64 (путь через `MSYS2_ROOT`); Linux-VM не нужна.
  При реально удалённой среде выбирать доступный транспорт, не требовать device_bash.
- Единственный источник мода — подмодуль `mods-src/BBSC`.
  Правки, тесты и сборка выполняются в нём. Сначала проверить status/HEAD
  подмодуля и pin родительского репозитория; не делать автоматический reset/update.
- Основной код: `emulator/src/core/bloodborne_re.cpp`, `emulator/mod/`;
  сервер: `server/gameserver`; порт/лаунчер: `src/`, `gpu/`, `launcher/`, `packaging/`.
- Игровой случай исправлять общим правилом; `mods-src/BBSC/tools/gamedata` помогает найти
  аналогичные события. Чужие правки, third-party submodule и __pycache__ не коммитить.
- Общая установка ПК `<путь-установки>` для всех
  локальных клиентов. Проверять наличие перед операциями.
- Профиль `%LOCALAPPDATA%/Bloodborne Game Launcher` (PROFILE_NAME в bbport_paths.py).
  DLL: `<install>/coop/client/bbsc`; данные: `<profile>/coop`, через BBSC_DATA_DIR.
  bbgl/bbport-coop — прежние профили, не выбирать автоматически при наличии текущего.
- `tools/coop-dev/coopdev.ps1` доступен локально с явными -Install/-Root.
  Выбор профиля исправлен 01.11: текущий Bloodborne Game Launcher имеет приоритет,
  legacy используется только при его отсутствии. status выводит profile/settings_file/
  bbsc_data/game_log; перед операциями проверять эти пути. SSH VPS — через
  ssh-my-devices при необходимости.

## Изменения и сборка

Для синхронизации учитывать хоста/гостя, загрузки, переподключение, краш и сохранение.
T26 runtime-переключение отменено: Офлайн / Совместно выбираются при запуске.
Не возвращать эксперимент без новой просьбы.

Проверки выбирать по изменённой логике, включая негативные пути и реальный native
control flow для хуков. Для menu exit существуют tools/test_menu_quit.py и
 tools/test_hook_resume.py; post-load recovery — отдельный набор. Перед запуском
проверить команды/зависимости в текущем дереве.
Следовать docs/TESTING.md: только затронутое поведение и прямые
зависимости, без полного discover и повторов без новых изменений. Проверки
сейвов/восстановления (включая post-load, миграции и хэши живых сейвов) исключены
из стандартного прогона по разрешению пользователя. Существующие тесты сохранить
для запроса/регрессии; смешанные файлы запускать по отдельным нужным методам.
Для изменения самой логики сохранения/восстановления нужны целевые проверки.
Тесты мода запускать в подмодуле; не дублировать проверки без новых изменений.

- Мод: из нужного дерева `emulator/mod/build-mod-bbport.cmd`, результат build/mod,
  лог build/mod-build.log, exit=0. Собирать только подмодуль.
- Полный пакет из корня checkout в MSYS2 CLANG64:
  `bash packaging/windows/build-coop-package.sh`.
  Он собирает bundled мод, порт и пакет с Party; отдельный сервер не собирается.
  BB_FAST_DEPLOY=1 пропускает verify-release.py по правилам обычного деплоя.
  SKIP_BUILD=1 пропускает порт: допустим только при доказанной актуальности exe.
- Staging: `out/stage/Bloodborne Game Launcher`;
  ZIP: `dist/bbgl-<версия>-windows-x64.zip`. Актуальные имена сверять со скриптом.
- Код фиксировать перед тестовой сборкой по принятому процессу, не захватывая
  чужие изменения. В документационной ревизии коммит не обязателен без просьбы.
  Push только по просьбе, в наш remote; не выдумывать coauthor/session metadata.

## Деплой, сейвы и тест

После исправлений и успешной сборки пользователь ранее разрешил деплой своей
сборки на остановленный ПК. Сначала бэкап заменяемых файлов; быстрый деплой по
правилам выше. Не завершать игру/лаунчер ради деплоя; при любом работающем локальном
экземпляре отложить замену общих файлов и сообщить. Обновление VPS не следует из
документационной ревизии; при серверной правке сравнить действующий код и сделать
бэкап перед согласованным деплоем. Не трогать shadnet без основания и авторизации.

Сейвы не откатывать автоматически. Реальные user_dir проверять отдельно по каждому
локальному профилю и свежим логам; прежний testHost — исторический путь. `ddd` — друзья.
Снимки `forest-host` и оба `chalice-test-20261030` сохранить. Восстановление —
по просьбе, только при закрытой игре, с резервной копией текущего полного SPRJ0005
и связанных BBSC metadata/journals. Оригинальные сейвы не использовать для опытов.

Перед прогоном зафиксировать время/версии/роли/сценарий. Дать короткие шаги и
наблюдаемый критерий; по запросу запуска запустить игру самому; игровой результат подтвердить с пользователем.
После «готово» собрать timeline/mod/game/captures всех локальных участников и серверные
логи при необходимости. Сопоставлять время и события, а не только искать ERROR.
При вылете проверять полный last_run.log/native Fault/stack/exit code и Windows
Application/System/WER. Исторический nvlddmkm/141 не доказывает причину нового
вылета. После bbaae0f reader должен жить после закрытия окна до выхода игры.
Факт исправления reader не означает исправление boss-wipe crash.

Находки/статусы записывать в HANDOFF/BACKLOG и соответствующий fixes doc,
с границами подтверждения. Если поздний результат заменяет раннее «pending»,
пометить раннюю запись исторической, не возвращать закрытый сценарий в план.

Файлы игры только читать; не включать в пакет. Не выводить settings.json целиком,
пароли/ключи/токены. Не менять SSH/firewall. Релизный ZIP — навык bb-coop-release.
