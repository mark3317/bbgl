# Подготовка релиза BBGL

Пути относительно корня текущего checkout, а Markdown-ссылки — относительно
этого файла. Подготовка другой машины: [WORKSTATION.md](../../../docs/WORKSTATION.md).
Путь установки и MSYS2 определять на текущем устройстве; примеры старых
машин в исторических документах не использовать как defaults.

## Цикличные обработки — только с разрешения пользователя, 06.11.2026

Любые новые цикличные обработки в моде (периодические опросы, таймеры,
ticks, фоновые проверки и повторы), в том числе внутри существующего
обработчика, добавлять только после явного разрешения пользователя
на конкретный механизм. Общая просьба исправить баг или добавить функцию
не считается таким разрешением. Обоснованная невозможность штатного решения
тоже не заменяет разрешения. До согласования описать назначение, период,
объём работы и ожидаемую стоимость; сначала искать штатный событийный путь.
Такие обработки не должны ухудшать общую оптимизацию: оценивать суммарную
нагрузку, включая простой и рост числа игроков/объектов, и проверять влияние
на производительность. При обнаружении регрессии устранить её до принятия
изменения; одно разрешение на механизм не означает согласия на ухудшение.

## Приоритет штатной реализации — 06.11.2026

При любых изменениях и новых доработках BBGL/BBSC сначала искать и пробовать
использовать или корректировать штатные условия и обработки игры/порта.
Снятие конкретной штатной блокировки предпочтительнее нового обработчика,
опроса, сканера, очереди, сетевого сообщения или повтора. Новый механизм
добавлять только при обоснованной невозможности штатного решения;
объяснить ограничение и стоимость, сохранить native control flow и авторитет.
Это не расширяет запрос сборки/логов до самостоятельной правки кода.
Перед изменением поведения/оптимизацией читать
[накопленные знания](../../../mods-src/BBSC/docs/OPTIMIZATION.md).


Предпочтение пользователя от 05.11.2026: запрос «подготовь релиз» включает весь процесс ниже. Перед push дать пользователю тексты релизов и оба готовых ZIP для проверки. Подготовка архива не разрешает push, публикацию или установку на устройства.

Репозиторий: <корень-checkout>. Сначала читать его AGENTS.md, mods-src/BBSC/docs/HANDOFF.md, docs/ROADMAP.md, верх CLAUDE.md, BUILDING.md и docs/TESTING.md. Для правок мода — его AGENTS.md, верх CLAUDE.md и BACKLOG.md. Единственный источник мода — mods-src/BBSC; перед правкой/сборкой сверить status, HEAD и родительский gitlink. Не захватывать чужие изменения, сторонние подмодули и Python-кэши в свои коммиты. Если пользователь просит дождаться коммитов — остановить изменения и сборку до завершения фиксации.

## Подготовка

- Найти предыдущий релиз по локальным тегам/истории; изучить весь diff до текущего дерева, включая изменения BBSC и уже описанные фиксы. Отличать исходники, успешную сборку, установку и подтверждение в игре. Не объявлять исправленным то, что прошло лишь fixture или запуск процесса.
- Удалять только подтверждённо неиспользуемые остатки. Не удалять полезные отчёты/инструменты только из-за возраста. Согласовать актуальные инструкции с реальным запуском; исторические серверные документы явно помечать как историю.
- Проверить релизные defaults в исходниках и окружении: подробные логи, research, профилирование, Vulkan validation, debug и читы выключены, ошибки остаются видимыми. Рабочие хуки коопа не отключать ради тишины. Не сбрасывать существующие личные или тестовые профили; не выводить settings.json целиком.
- Обновить версии лаунчера, тег обновления, mod.json, строку версии DLL и имя ZIP в упаковке. Релиз лаунчера называть BBGL <версия>, без BBSC-GL в заголовке.
- При подготовке релиза обновить документацию обоих проектов. Для BBGL обновить README на русском и английском, changelog, BUILDING, инструкции в ZIP и актуальные handoff/roadmap. Для BBSC-GL обновить `mods-src/BBSC/README.md` и `README.ru.md`, актуальные HANDOFF/BACKLOG и затронутые инструкции мода. Указать версию, основные изменения, совместимый выпуск BBGL и границы игровых проверок. Закоммитить документацию мода вместе с его версией перед закреплением коммита в BBGL.
- Подготовить отдельные тексты релизов BBGL и BBSC-GL с реальными изменениями с прошлого выпуска, установкой, совместимостью и ограничениями. Не выдавать подготовку за уже опубликованный релиз.
- Проверить локализацию на обоих языках — английском и русском. Проверять не только словарь: главный экран, все разделы настроек, мастер, варианты списков, подсказки и динамические сообщения/ошибки; сохранять подстановки. Смотреть переносы, высоту строк, кнопки и обрезание при обычном и минимальном размере окна. Для текущего QML использовать tools/capture_release_screenshots.py --language en|ru --review --output out/<каталог>; дополнить просмотром готового frozen EXE. Если найдены исправления в релизном коде, пересобрать ZIP и обновить проверки. Статический словарь, Qt/offscreen и запуск EXE не заменяют визуальный контроль добавленного игрового интерфейса на обоих языках; если игра не проверена, явно оставить этот статус открытым.
- Переснять скриншоты текущего интерфейса. tools/capture_release_screenshots.py рендерит настоящий QML в изолированном профиле без игры/сети; проверить изображения глазами. Не использовать старые картинки или выдуманные игровые результаты. Русские игровые термины сверять с msg/rusru; offscreen Qt не заменяет игровой визуальный контроль.
- Запускать только затронутые проверки и прямые зависимости по docs/TESTING.md. Не повторять полные прогоны ради упаковки; save/recovery проверки не входят в стандартный набор.

## Чистый ZIP

Перед сборкой прочитать packaging/windows/build-coop-package.sh, package.sh, bundle-coop.py и verify-release.py. Проверить разрешённые абсолютные staging/dist пути: package.sh пересоздаёт staging. Нельзя использовать установленный лаунчер с пользовательскими данными как источник архива.

Из корня checkout в **MSYS2 CLANG64**, подготовив зависимости по
[BUILDING.md](../../../BUILDING.md):

```bash
mkdir -p out
unset BB_FAST_DEPLOY SKIP_BUILD COOP_INVITE COOP_NAME
bash packaging/windows/build-coop-package.sh > out/release-build.log 2>&1
```

Дождаться успешного exit сборки и упаковки. Текущий путь — встроенный Party/P2P, без отдельного сервера и аккаунта shadNet. Проверка релиза не должна требовать удалённые серверные файлы. Сохранить обязательные runtime и лицензии; случайные системные DLL не добавлять.

Выходы: out/stage/Bloodborne Game Launcher и dist/bbgl-<версия>-windows-x64.zip с .zip.sha256; точные имена сверять со скриптом. verify-release.py выполняется один раз внутри package.sh; не повторять его для того же staging после успеха. Проверить CRC/структуру ZIP при изменении упаковки и провести smoke frozen-лаунчера в изолированном профиле при изменениях его сборки/старта. Не завершать работающие игры.

Перед публикацией проверять обязательные файлы **в самом итоговом ZIP**, включая Bloodborne.exe, run.py, runtime DLL/Python и лицензии; CRC не доказывает полноту архива. Сверять список и содержимое записей с проверенным staging. Smoke выполнять из распакованного итогового ZIP в изолированном профиле, а не только из staging. При обновлении документов/метаданных не терять остальные записи; после перепаковки заново проверить полноту.

Проверить отсутствие настроек, сохранений, аккаунтов, own-world/item-ledger/bell-pending, логов/дампов/бэкапов, секретов и игровых файлов в ZIP. Дельты модов и необходимые иконки отличать от оригинальных архивов игры. Запись commit в SOURCE.json не означает чистый источник: учитывать source_dirty и соответствие gitlink.

## ZIP для BBSC-GL

Для каждой новой версии BBSC-GL обязательно подготовить `dist/bbsc-gl-<версия-мода>-windows-x64.zip` из проверенного итогового Windows ZIP соответствующего BBGL. Если BBGL уже опубликован, сверить SHA-256 исходного ZIP с опубликованным файлом. Версию мода из `coop/SOURCE.json` сверить с `mod.json`, `bundle.json` и тегом BBSC-GL. Коммит мода из `coop/SOURCE.json` сверить с коммитом подмодуля в релизном теге BBGL и с коммитом тега BBSC-GL.

- Перенести из итогового ZIP BBGL `coop/client/bbsc/bbsc.dll`, `coop/client/bbsc/bbsc-launch.exe`, `coop/client/bbsc/mod.json`, весь `coop/party/`, `coop/client/bundle.json`, `coop/SOURCE.json` и лицензии мода и Party (`licenses/BBSC-LICENSE.txt`, `licenses/NoDreamForHunter-LICENSE.txt`). Копировать готовые файлы из архива без пересборки. Папки `coop/` и `licenses/` должны лежать в корне ZIP мода, чтобы его можно было распаковать в папку с `Bloodborne.exe`.
- Сверить список файлов с составом коопа в релизной упаковке, проверить CRC и побайтовое совпадение с исходным ZIP BBGL. Убедиться, что `source_dirty` равен `false`, а в архиве есть только перечисленные компоненты и лицензии.
- В описании релиза мода на русском и английском указать точную совместимую версию BBGL, установку при закрытой игре и лаунчере в папку с `Bloodborne.exe`, а также ссылку на полный ZIP BBGL для первой установки.

Предоставить оба ZIP, размеры, SHA-256, состав, версии и тексты релизов. Явно назвать незавершённые проверки. Push и публикация только после отдельного указания пользователя. Реальные сейвы не менять, игровые файлы только читать.

## Публикация на GitHub

Предпочтение пользователя от 07.11.2026: для каждого выпуска BBGL
публиковать **два отдельных GitHub Releases**. Разрешение опубликовать
конкретный BBGL включает отправку соответствующих исходников обоих
проектов и публикацию релиза закреплённой версии BBSC-GL. Подготовка
по-прежнему требует отдельного указания перед публикацией.

1. Сверить коммит и версию мода в `coop/SOURCE.json` итогового ZIP с
   gitlink и версией в релизном коммите BBGL. Проверить чистоту исходников
   и адреса репозиториев.
2. Сначала отправить закреплённый коммит и тег в `mark3317/bbsc-gl`.
   Проверить удалённый тег. Подготовить GitHub Release с названием
   **BBSC-GL <версия мода>** и собственным описанием изменений мода
   на русском и английском. Прикрепить проверенный ZIP мода к релизу в
   `mark3317/bbsc-gl`. Если релиз той же закреплённой версии уже опубликован,
   использовать его и добавить ZIP при отсутствии. Если ZIP уже прикреплён,
   сверить состав и содержимое и использовать его при совпадении. При
   расхождении сообщить о нём и остановить публикацию до выяснения причины.
3. Отправить релизный коммит и тег BBGL в `mark3317/bbgl`. Подготовить
   GitHub Release **BBGL <версия лаунчера>** с согласованным описанием,
   проверенными Windows ZIP и SHA-256 и ссылкой на релиз BBSC-GL.
4. Опубликовать релиз мода, затем релиз лаунчера. Публикация BBGL ждёт
   успешной публикации соответствующего BBSC-GL. Проверить обе страницы
   релизов, теги, взаимные ссылки и файлы BBGL. Скачать ZIP мода с GitHub
   и сверить SHA-256 с подготовленным архивом. Если используется уже
   опубликованный ZIP, сверить его состав и содержимое с итоговым ZIP BBGL.
   В итоговом сообщении дать ссылки на обе страницы GitHub Releases и ZIP мода.
