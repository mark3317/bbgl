# Проверки BBGL и BBSC-GL

## Выбор проверок — 01.11.2026

Выбирать тесты по изменённому поведению и его прямым зависимостям. Полный discover,
все C/C++ harness и игровые прогоны не запускать при каждой доработке/упаковке.
После успешной проверки повторять её только при новых изменениях, сбое или
неразрешённом сомнении. Для правок документации достаточно diff --check.

По разрешению пользователя проверки сейвов и восстановления исключены из
стандартных и обязательных прогонов: post-load recovery, own-world/item recovery,
сохранность сейвов при миграции/обновлении и сравнение хэшей живых сейвов.
Их существующие файлы сохранены для отдельного запроса/расследования регрессии.
В смешанных test-файлах выбирать нужные методы, а не запускать весь файл ради
одной несвязанной проверки. Для изменения самой логики сохранения/восстановления
выполнять непосредственно необходимые проверки; без этого не заявлять её проверенной.
Это правило не отменяет запрет менять реальные сейвы без просьбы пользователя.

- Лаунчер/мастер/маршрутизация: соответствующие test_setup_wizard,
  test_startup_routing, test_launcher_defaults; остальные UI-тесты по затронутому экрану.
- Кнопки/файловые моды: нужные методы test_setup_wizard, test_mods;
  test_file_mods.c только при изменении native файлового слоя.
- Графика/меню/шейдеры/ввод: соответствующие tests/test_*; не собирать все harness.
- Помощник путей/логов: tests/test_coopdev_profile.ps1; реальный collect только
  при изменении сбора логов. Без обязательного чтения/хэширования сейвов.
- Сессии BBSC: test_menu_quit при изменении выхода/его порядка;
  test_hook_resume при изменении trampoline/hooks; test_native_leave_release
  при изменении native leave. test_post_load_recovery не входит в стандартный набор.
- Чаши/follow/matchmaking: test_chalice_scope / test_follow_arrival /
  test_matchmaking_native соответственно. Очереди/scaling — test_pending_work;
  фильтрация диагностик/cache — test_perf_policy. Не запускать их для чистой правки UI.
- Native сеть/диагностика: test_coop_latency_diagnostics и test_p2p_latency_transport
  только при изменении транспорта/его логирования.
- Пакет: verify-release.py вызывается ОДИН раз внутри package.sh. Не повторять
  вручную после успешной упаковки того же staging. Проверка ZIP нужна при
  изменении упаковки/архивации; smoke собранного лаунчера — при изменении
  заморозки, зависимостей, запуска или жизненного цикла процесса.
- Мод проверять в дереве, которое собирается (для пакета mods-src/BBSC).
  Если код и тесты двух checkout одинаковы, не дублировать прогоны в соседнем BBSC.
  Если отличаются, сначала установить, какая версия действительно входит в пакет.
