## Точки измерения

`SubmitFlipInternal`: время PrepareFrame/PrepareBlankFrame и момент постановки
полностью подготовленного request в очередь под существующей mutex.
Это готовность request на CPU, а не доказательство завершения GPU rendering.

Оба пути PresentThread (внешний vblank и внутренний immediate loop) используют
одну запись измерений, с сохранённым deadline **до** advance_slot:

- `ready_late_ms`: max(0, enqueue − deadline). К сроку не было готового request.
- `ready_by_deadline`: число кадров, уже стоявших в очереди к сроку.
- `dispatch_ms`: dispatch start − max(enqueue, deadline). Готовый request
  обслужен позже доступного слота. Сюда входят scheduling, mutex и vblank logic;
  это не отдельный счётчик вытеснения ОС.
- `queue_ms`, `queue_depth_max`: пребывание в очереди и глубина при dequeue.
- `prepare_ms`: wall time подготовки, включая возможные ожидания внутри Vulkan.
- `flip_ms`: весь вызов Flip, включая существующие telemetry/capture/IRQ paths.
- `period_ms`/`period_max_ms`: эффективный период, учитывает FG flip limit;
  `limit` — исходный configured cap. `strict`/`grid` фиксируют режим ограничителя.
- `cap_waits`, `cap_wait_ms`, `cap_wake_ms`: только реально выполненные ожидания
  next_flip. Wake lateness измеряется сразу после возврата из precise/обычного сна.
- `tail_wake_ms`: lateness общего vblank sleep, только если его deadline ещё
  был впереди при входе. Если deadline уже прошёл, это отдельный `tail_overruns`
  и `tail_overrun_max_ms`, а не ложное «сон опоздал».
- `producer_waits`/`producer_wait_ms`: ожидание непустой request queue через CV,
  включая ожидания, закончившиеся очередным vblank timeout.

Раз в ~5s: PID, epoch_ms, реальные duration_ms/frames; средние и максимумы.
`Perf pacing slow` сохраняет первые8 интервалов/Flip >50ms за окно с их временем
и той же декомпозицией; `slow_omitted` считает остальные. Печать отложена до
отчёта, heap/vector/sort и OS CPU queries на каждом кадре не добавлены.
Новые Clock::now и атомики имеют собственную небольшую, пока не измеренную цену.

В SwapThread отдельно суммируются wall time ожидания presenter job и работы
SetHDR/Present (`swaps`, `swap_queue_us`, `swap_work_us`). Эти атомарные totals
приблизительны у границы окна: обновления отдельных счётчиков не являются одним
атомарным snapshot. Они относятся к завершившимся заданиям, не обязаны совпадать
с frames данного окна; не складывать их с flip_ms как независимые CPU расходы.
При отключённом separate swap та же работа выполняется синхронно внутри Flip.

## CPU и влияние наблюдения

Windows GetProcessTimes/GetThreadTimes/GetSystemTimes вызываются на границах
окон. `process_cores`/`present_cores` = CPU milliseconds / wall milliseconds:
1.0 означает одно полностью занятое логическое ядро, а не1% общей машины.
`system_busy_pct` — общая загрузка машины, её нельзя суммировать между играми.
`cpu_valid=0` обозначает сбой получения CPU данных, неизвестное не равно нулю.
Linux использует getrusage, системная загрузка там обозначается -1.

CPU baseline после печати обновляется; `previous_report_ms` в следующем отчёте
показывает стоимость предыдущего диагностического отчёта. Интервалы между
flip всё равно включают паузы вывода; высокий report_ms надо учитывать при
интерпретации dispatch/slow. Старые Perf window/Perf stall остаются совместимыми.
Время Record передаётся по steady_clock; epoch для slow привязан к началу Flip.

Новые замеры активны вместе с существующим BB_PERF_CAPTURE (default true).
`BB_PACING_CAPTURE=0` отключает именно новый слой. Пользовательские настройки
не переписаны. Это диагностика, не новый пользовательский UI переключатель.

## Как анализировать будущие данные

`tools/coop-dev/summarize-pacing.py log1 log2 log3 --start-ms N --end-ms N`
берёт только полные окна, разделяет PID/configured cap/strict/grid. Средние
per-frame полей взвешены по frames, wake — по числу соответствующих ожиданий,
CPU — по wall duration. Повреждённые/перемешанные строки считаются и пропускаются;
дубли/перекрытия одного PID/config отклоняются. Отсутствующие поля дают null.
При меняющемся effective FG period отрезки выбирать отдельно: конфигурация
cap может остаться прежней. При переводе системных часов окно нельзя считать
надёжно синхронизированным только по epoch_ms.

Будущий контролируемый сценарий: одна игра при60 в одной сцене, затем три
в той же сцене/разрешении/режиме, включая неактивные окна. По runtime логам
фиксировать загрузки, роли и интервалы; исключать меню/переходы/первый запрос
после паузы. Предполагаемый эффект scheduling не выводить из одного процента
CPU. Готовая очередь + большое dispatch/wake укажет на путь обслуживания;
большое ready_late — на upstream нагрузку (CPU/GPU ещё нужно различить).
Окончательное доказательство preemption потребует OS trace, если этих данных
окажется недостаточно. Игровой сценарий сейчас не запускался.
