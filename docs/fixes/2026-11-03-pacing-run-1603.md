## Подтверждённый недобор на пути ограничителя

Выбраны только окна до первой готовности мира соответствующего игрока, где
ready_by_deadline=frames (это меню/переход до игровой загрузки, НЕ gameplay
benchmark). Их не отбирали для оценки общего FPS, а для проверки условия:
«request уже готов, насколько поздно его забирают?».

| Игрок | Окон / секунд | FPS | Готово к сроку | dispatch mean,мс | tail wake mean,мс |
|---|---:|---:|---:|---:|---:|
| P1 |1 /5.011|57.28|100%|0.802|0.801|
| P2 |3 /15.025|57.10|100%|0.857|0.856|
| P3 |1 /5.016|57.42|100%|0.760|0.759|

Во всех выбранных окнах cap_waits=0, queue_depth_max=2, ready_late=0.
P1 окно15:57:06–11, P2 примерно15:56:59–15:57:14, P3 15:57:00–05.
Целевой period16.667ms, strict1/grid0. Процессы занимают~0.45–0.56 CPU cores;
system busy35–72% в отдельных этих окнах (у других игр могли идти загрузки).
Это не изолированный single-game A/B, но отсутствие готового кадра исключено
именно для выбранных запросов. Dispatch практически полностью совпадает с
опозданием tail sleep. В P2 отдельный wake17.182ms; средняя потеря~0.86ms/frame.

В коде внутренний cap wait уже использует Common::PreciseSleepUntil, но внешний
vblank tail всё ещё std::sleep_until. При готовой очереди и cap60/vblank60 кадр
часто обслуживается внешним путём. После позднего пробуждения relative cap
снова отсчитывается от текущего времени. Наблюдённые~0.8ms объясняют57 вместо60.
Готовый request на CPU не означает завершённую GPU работу, однако в этих окнах
узкое место именно до dispatch, а не время обработки presenter job.

## Цена диагностик

previous_report_ms в отдельных игровых окнах до14.074ms. Новый отчёт способен
внести редкую дополнительную задержку раз в5s; это наблюдаемая цена, её нельзя
игнорировать. Но она не объясняет почти постоянное опоздание~0.8ms **каждого**
кадра готовой очереди и десятки поздних кадров за35s. Slow capture ограничен
8 записями на окно, поэтому максимум списка slow не обязан совпадать с худшим
Perf window кадром. Для причинного CPU/GPU вывода нужно учесть logger/reader.

## Подготовленная правка — только исходники

В VideoOutDriver::PresentThread внешний tail sleep при strict_cap теперь
Common::PreciseSleepUntil(tick_deadline), как внутренний cap wait.
Обычный сон сохранён для non-strict. Deadline/advance_slot/частота vblank/
правила очереди не менялись; ускоряющий catch-up не вводится.
Новые отчёты имеют tail_precise=1 для различения реализации.

У helper последние500us могут быть spin-wait. Верхняя ориентировочная добавка
при60Hz для3 игр:3*60*0.5ms=90ms CPU/s (~0.09 logical core), но реальный
эффект при уже высокой загрузке надо проверить. РостFPS/устранение статеров
не заявлены. Правка не собрана/не установлена, игры не запускались.
Targeted whitespace и printf argument-count checks PASS; нового C++ выполнения нет.

Следующий шаг после будущей разрешённой сборки — проверить tail_wake/dispatch
и ready_by_deadline отдельно; для нагрузки нужен matched одна vs три игры.
Если late-ready остаётся при одной игре, разносить CPU игрового tick/render/
защиты памяти и GPU readiness, не сокращать gameplay tick наугад.
