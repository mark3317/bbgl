Обновление: блокирующие пути и повторные memory checks исправлены в исходниках.

## Источники и границы

Свежий завершённый запуск `all-current-three-20261103-162200`, parent d588b23 /
BBSC ac5e70b плюс рабочие изменения. Сборка уже включает precise vblank tail.
Собраны 9 mod/native/bbnet файлов трёх профилей в
`out/coop-dev/runs/perf-review-20261103-1623/pc`: warnings=0,
ChangedDuringCopy=false у всех файлов. Игр к моменту сбора нет.
P1 PID26556, P2 PID12068, P3 PID30784; по 36 pacing окон, malformed=0.
Одна неполная перемешанная строка Perf window у P3 исключена, а не восстановлена.
Анализ воспроизводится `analyze.py`; результаты `segment-metrics.json`, `analysis.txt`
в каталоге сбора. Settings/сейвы не копировались и не менялись.

Три игры работали на одном ПК с 12 логическими CPU, у каждой 6 draw-preparation
workers + scanner; вывод 1280x720, raster 1280x720. Это тест нескольких игр на
одном устройстве, не эквивалент сетевого коопа с одной игрой на устройство.
P1 остаётся один; P2 guest/P3 host с двумя охотниками примерно 16:25:35–16:25:59.
Трёх игроков в одном мире не зафиксировано. Сценарий/камеры между версиями не
контролировались: общий FPS нельзя использовать как доказательство регрессии версии.

## Средний игровой FPS и поздние кадры

Таблица по полным Perf pacing окнам внутри интервалов; границы окон процессов
различаются. Каждый короткий интервал содержит около 15 секунд измерений,
последний около 30 секунд. CPU — общий по машине, не сумма процентов профилей.

| Интервал МСК | P1 FPS | P2 FPS | P3 FPS | Общий CPU |
|---|---:|---:|---:|---:|
| 16:24:50–16:25:10, все до соединения | 47.17 | 49.65 | 47.01 | 98.2–98.3% |
| 16:25:38–16:25:58, P2 guest/P3 host | 53.66 | 54.82 | 54.86 | 94.7–94.8% |
| 16:26:15–16:26:50, после выхода гостя | 50.49 | 52.64 | 52.86 | 96.4–96.5% |

Три процесса вместе занимают около 9.0/9.4/9.4 логических CPU соответственно;
остаток system busy принадлежит другим процессам/системе. Почти полная загрузка
CPU подтверждена, но распределение ожиданий CPU/GPU требует дополнительных
замеров; готовность request на CPU не измеряет завершение GPU.

В паре ready_by_deadline=69.3/76.5/85.6%, ready_late=1.87/1.50/1.54 мс/кадр,
dispatch=0.128/0.098/0.039 мс. После пары ready_late=3.03/2.21/2.24 мс,
dispatch=0.146/0.142/0.036 мс. В этих окнах подготовка request занимает в среднем
0.22–0.39 мс; swap work 0.52–0.72 мс, swap queue 0.04–0.20 мс. Эти wall times
не являются GPU timestamp и не исключают ожидание GPU ранее по конвейеру.
Основной остаточный недобор возникает до enqueue, не в точном tail sleep.

Статтеры есть также у одиночного P1 и до создания пары: один сетевой обмен
между уже соединёнными игроками не объясняет весь недобор. Число workers само
по себе не доказывает конкуренцию: `BbThreads::MakeBackground()` действительно
ставит THREAD_PRIORITY_IDLE на Windows. Уменьшение BB_PREP_WORKERS требует A/B,
без проверки может ухудшить подготовку команд.

## Отдельные большие статтеры

1. **P3, 16:25:03.661: 505.592 мс**. ready_late=488.915 мс,
   dispatch=0.011 мс, prepare=0.168 мс. В том же 10s mod окне
   `trace ChrAction.UseItem.NativeApply` max=474946 us. В 16:25:03.626 и
   16:25:03.631 записаны два успешных запроса разрешения Beckoning.
   `TraceEntry` вызывает синхронный `PartyAcquire()` перед выполнением предмета;
   `Call(/party/acquire, {}, 8500)` выполняет WinHTTP send/receive/read на потоке
   вызова. Это конкретный подтверждённый блокирующий путь игрового хука,
   хорошо объясняющий большую часть данного кадра. Подробного разложения
   475 мс на HTTP/consensus/вытеснение нет; не объявлять все 506 мс чистой сетью.
   Два хука исполнения (0x018F9720/0x018C9160) вызывают gate: проверить, не
   дублируется ли запрос одной операции; логи доказывают два вызова, не два
   независимых consensus round trip одинаковой длительности.
2. **P1, 16:26:22.672: 435.795 мс**. ready_late=418.546 мс,
   dispatch=0.582 мс, prepare=0.245 мс. Перед этим 16:26:22.210 stale claim
   timeout; 16:26:22.647 завершение HTTP cleanup. `ClearStaleRecord()` вызывает
   синхронный Post под summon_lifecycle_mutex; та же mutex используется
   `SendCleanSummonCreate()` и фоновым `MaintainSummonLifecycle()`.
   Совпадение и потенциальный путь блокирования установлены, но нет thread-id/
   duration/lock-wait для этого вызова. Причинность конкретных 436 мс пока НЕ
   доказана. Нельзя просто удалить ordering delete-before-create: он защищает
   от повторного получения старого claim.
3. Дополнительные кадры P1 85–93 мс и P2/P3 100–113 мс тоже преимущественно
   late-ready; ни одно изменение tail limiter не устраняет их источник.

Перечень slow ограничен 8 записями на окно. Perf window и pacing имеют разные
границы, поэтому максимум/число кадров в соседних выборках нельзя приравнивать.
Например, sampled P2 111 мс в 16:26:48.589 относится к native окну, которое
заканчивается после границы 16:26:50 и не входит в полную оконную статистику.

## Постоянная нагрузка BBSC и влияние измерений

Полные 10s mod отчёты с концом внутри 16:26:15–16:26:50 дают верхнеуровневое
wall time BBSC около 4.70/4.50/5.99 мс на tick (P1/P2/P3), включая вытеснение,
ожидания и вложенные вызовы. Это не чистое CPU время и не измеренная потеря FPS
от DLL относительно офлайна. Вложенные scopes не складывать с родителями.

Приоритет изучения: IsValidSos.Update (в нём общий BBSC tick) около 2.88–3.28 мс,
ResponderBell.Availability около 0.54–0.87 мс. P1/P2 NpcPass около 0.39–0.49 мс,
у P3 около 1.49 мс, TalkStepBegin около 0.58 мс. NpcPass вызывается примерно
883–1002 раз/кадр; DreamTypeCheck около 417–436 раз/кадр. Каждый scope выполняет
два clock query и несколько атомарных операций; проверки памяти в hot hooks
запрашивают mapping/protection. Есть основание изучать быстрые выходы и повторные
проверки, но безопасное время жизни actor/map/event нужно сохранить. Scaling
в этой выборке около 0.17–0.24 мс среднего wall time: прежний giant scaling spike
не является первым объяснением наблюдённых кадров.

`previous_report_ms` достигает 18.827 мс у P1. Report печатается из PresentThread
раз в 5s; его стоимость реальна и может вызывать отдельный рывок. P2/P3 bbnet
содержат 7356/6832 packet-sample строк. `CollectDiagnostics()` форматирует весь
batch под transport mutex, общей с SendTo/RecvFrom; только сам LOG_WARNING идёт
после unlock. Это кандидат на редкие задержки socket calls. Длительность
format/mutex не измерена, виновность в конкретных кадрах не доказана.

`Frame stats`/GPU timing/compile counters в этом прогоне отсутствуют. Нельзя
считать runtime shader compiles нулём по отсутствию соответствующей диагностики.

## Порядок дальнейших изменений

1. Вынести party acquire с потока игры в подготовительную асинхронную операцию;
   native предмет допускать только по подтверждённому разрешению для актуальной
   попытки. Сохранить unanimous authority, отмену, смену поколения/роли, защиту от
   двойного применения предмета и отказ при потере связи. Не заменять gate простым
   cached can_beckon. Устранить повтор gate только с доказанным связыванием вызовов.
2. Добавить длительность и thread-id HTTP cleanup, wait/hold lifecycle mutex и
   packet-report formatting; затем увести длительный I/O и форматирование из
   общих critical sections с сохранением порядка lifecycle и транспорта.
3. Снизить observer overhead: отложенная печать pacing и выборочное измерение
   часто вызываемых hooks. Сначала сохранить возможность сопоставить результат.
4. Для общего FPS сравнить одну и три игры в одной сцене при тех же настройках;
   раздельно сравнить штатные 6 и меньше prep workers, снять CPU game/render/
   memory и GPU timestamps. Не урезать частоту gameplay tick и не менять приоритеты
   основной игры без измерений.

Это исследование: исходники продукта не менялись, сборка/деплой/запуск не
выполнялись. Исправление статтеров и стабильные 60 FPS в игре не заявлены.
