## Ранжирование по новым измерениям

Все значения — прошедшее время, не чистое время CPU. Средние нормированы на
игровые тики, охваченные BBSC-отчётами, а не на число выведенных кадров.
Для верхнего списка top10 отсутствующие записи дают нижнюю границу стоимости;
для основных трёх обработчиков записи есть во всех отчётах.
Вложенные scopes нельзя складывать с родителями. Дополнительно TalkStepBegin
вызывает NpcPass: общий счётчик `BBSC on top` не является точным эксклюзивным
временем всего мода и тоже не должен использоваться как сумма без пересечений.

**События NPC.** NpcPass вызывается в среднем715/707раз за игровой тик.
В худшей минуте П1,03:52, это825 вызовов/тик и2.825мс/тик;
общий BBSC tick там4.177мс/тик. Поиск NPC event составляет примерно0.256/0.277мс
(нижняя граница top10), поэтому один поиск не объясняет весь NpcPass.
Приоритет — повторные guards и чтения контекста, валидация памяти на каждый
шаг события, разделение общего контекста и индивидуального события.
Функциональные защиты загрузки, перемещения, личных квестов сохранять.

**Личные флаги.** Измерено1.95/1.91вызова RevertBbscNpcOwnFlags на тик.
Максимум35.780/63.415мс; >16мс31/36раз. Код делает восстановление
после tick и снова перед event/talk. Просто убрать второй вызов нельзя:
он защищает личный прогресс до исполнения событий. Кандидат — группировка
проверок памяти и уменьшение повторной работы внутри одного безопасного прохода.

**Периодические тексты — отдельный кандидат статеров.** TickBbscMessages
каждые2секунды заново ищет слоты FMG для всей таблицы сообщений и проверяет
уже установленные указатели. Наблюдались максимумы84.425/56.207мс;
>16мс129/396раз и >50мс по одному разу. Нижняя граница средней стоимости
по top10 около0.096/0.155мс на тик скрывает эту пакетную работу.
Кандидат — инвалидируемые по загрузке/смене FMG/языка индексы и переход к
переустановке при изменении контекста вместо полного повторного поиска.
Нельзя хранить невалидированный указатель через выгрузку репозитория.
Сами10секундные отчёты не дают точного времени каждого вызова: это доказанные
долгие исполнения внутри окна, а не доказательство причины каждого кадра.

**Колокола/предметы.** ApplyBbscBellsAnywhere вызывается из FinalResult.
Проверяет живые данные персонажа/сессии и наличие нужного предмета в инвентаре.
Диагностические строки уже ограждены Research=false; дорогие timings нельзя
списать на форматирование этих строк. Нужны подзамеры inventory lookup и
контекстных чтений, оптимизация проверок внутри вызова с сохранением немедленного
запрета предмета при входе/выходе из сессии.

самих измерений и возможное ожидание планировщика.

при oldest_ms0, П2 очередь0; waits/dropped/send_ms/dispatch_ms0.
Это не проверка задержки native UDP и не объяснение задержки смерти врага.

Рекомендуемый порядок: (1) повторный обход FMG/текстов для статеров,
(2) NpcPass и личные флаги для постоянной нагрузки,
(3) подзадачи общего tick и проверки колоколов. Сначала сохранить семантику
и адресные/поколенческие границы, затем сравнить одинаковый маршрут с теми
же включёнными замерами. Никаких новых правок игрового кода, сборки, установки
или запуска в этом анализе не выполнялось.
