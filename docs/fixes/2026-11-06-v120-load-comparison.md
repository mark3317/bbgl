## Что действительно добавилось после1.2.0

### 1. Независимые миры в покадровом tick — новый расход

В1.2.0 не было TickBbscWorldPresence/TickBbscIndependentWorld.
Теперь они запускают coordination/presence, выбор scope/owner, altars/snapshots,
blocks/lamps/travel/players и более поздние checkpoint/transition подзадачи.
Некоторые внутренние операции ограничены100мс/1с, другие всё ещё вызываются
каждый кадр; есть копирование membership и повторные проверки текущего контекста.
Точное время всей новой подсистемы отдельно не записано: общий2.8мс tick включает
и старые задачи. Нельзя назвать все2.8мс новой ценой независимых перемещений.

Рекомендация: выделить scopes для каждой подзадачи; dirty/work-сигналы на
смену presence/visit/map/lease/catalog. Между изменениями не собирать прежние
таблицы заново. Периодические heartbeat/liveness сохранить отдельно от подготовки
содержимого и не путать с постоянной пересборкой данных.

### 2. Независимый bootstrap внутри общего pre-event callback — главный новый кандидат

В1.2.0 callback уже существовал, но не выполнял GuardBbscWorldBootstrap,
EnableBbscNativeTravelEvent и новые проверки похищения/диагностические наблюдения.
Добавленный bootstrap на каждом шаге читает контекст/session/map, ищет event ID,
берёт presence mutex и в готовом мире снова вызывает block admission.
Порядка650–700 вызовов за тик умножают даже небольшой неизменный путь.

Рекомендация: один проверяемый снимок контекста внутри callback, единая
классификация immutable event descriptor, fast path готовности по world/map/load/
visit/lease/inventory revision. Полный admission повторять при изменении этих
идентификаторов и native readiness, а не безусловно для каждого ожидающего события.
Сначала измерить именно pre-event guard: имеющийся measure block admission
покрывает tick call, а не все вызовы из bootstrap. Не отключать сам барьер:
это вернёт непрогруженные миры, NPC и несогласованную историю смерти.

### 3. Native ownership/wake/packet filtering — новые расходы вне полного профиля

После релиза введены обход NPC/блоков для native владения, wake begin/end,
фильтрация пакетов по владельцу и дополнительные пути native HP.
Владельцу теперь необходимы original dirty HP producer и native receive в одном
кадре. Время самой оригинальной receive-ветви не равно времени callback,
переключившего в неё исполнение, и может отсутствовать в счётчике BBSC.
Это нельзя безопасно выключать ради FPS: прежняя задержка смерти показала,
что одна роль receive или отключённый dirty producer ломают синхронизацию.

Рекомендация: отдельные counters/time для send/receive/handle lookup и native
HP проходов, число акторов/блоков/пакетов; не перечитывать одинаковый map/scope
для каждого NPC в рамках одного прохода. Историю/инвентарь блока готовить по
native изменениям/streaming, не создавать новый snapshot без новой информации.
Средние capture/owner mutex сейчас малы; переписывание сети/блокировок целиком
имеет меньший приоритет, чем pre-event и общий tick.

### 4. Личные native NPC-контроллеры

LocalEvents в bbsc_quest_event_rules.h расширены50→69 (+19 native controllers).
Это +38% элементов именно этого списка, НЕ +38% CPU и не всех игровых событий.
Выросло число разрешённых локальных native сценариев; их выполнение игрой может
добавлять работу вне BBSC callback. Число личных NPC-флагов изменилось822→826,
так что падение FPS нельзя объяснять кратным ростом количества этих флагов.

Рекомендация: переносить неизменную классификацию/локализацию на создание и
native restart события; обычный ожидающий шаг должен делать минимальные проверки.
Сохранить повторную защиту в тех местах, где native reset возвращает net byte.
Не вырезать19контроллеров целиком: они исправляют личные состояния NPC и
предотвращают чужой прогресс/дубли. Если понадобится упрощение функциональности,
оно должно быть отдельным согласованным решением, а не скрытой оптимизацией.

## Что дорого, но уже было в1.2.0

- RevertBbscNpcOwnFlags и два прохода перед tick/event/talk уже существовали.
  Их нельзя считать целиком новым расходом. Групповые чтения уже снизили
  сопоставимые Cathedral averages0.548→0.474мс у хоста и0.241→0.212мс у гостя.
  Следующий вариант — отслеживать изменение группы/личного журнала и пропускать
  неизменённую работу при доказанной актуальности, сохраняя native receipt пути.
- TickMessages с2секундным полным поиском строк уже был в1.2.0. Исправление
  дало129→9 и396→19 вызовов>16мс в последующих прогонах, >50мс теперь0.
  Это устранённая старая неэффективность, не доказательство новой регрессии.
- TickScaling/проверки таблиц и BellsAnywhere уже были в1.2.0. Пик scaling table
  owners69мс у П2 реален, но тут уже есть1Гц idle guard и кеш смещения таблицы.
  Нужны cache hit/miss/invalidation и стоимость каждого lookup, затем устранение
  повторных поисков. В1.2.0 аналогичный пик мог быть, старых измерений нет.
- Синхронный backup перед применением прогресса — отдельный загрузочный расход,
  сейчас до152мс. Не удалять обязательное резервирование ради FPS.

По parent diff v1.2.0→рабочее дерево нет изменений в gpu/src рендерера порта.
Это не исключает GPU contention, streaming, настройки или другую версию
установленного бинарника, но исходники не указывают на новый renderer hot path.

## Что убрать из обычного запуска прямо по смыслу

Убрать именно сбор диагностик из normal mode: PERF scopes/timers/atomics,
NPC lifecycle sampling, combat trace и подробный timeline должны быть явным
режимом расследования. В1.2.0 релизная диагностика была выключена; последние
сравниваемые прогоны намеренно включали её. Накладные расходы особенно заметны
при сотнях callback/frame. Нельзя выдавать результат «диагностика ON против
релиза OFF» за чистую регрессию функционального кода.

Эти переключатели уже выключены в релизных defaults; речь о подготовленных
диагностических профилях, а не о новом глобальном запрете логирования.

Для контрольного замера оставить кадровой PACING, но отдельно выключить
BBSC PERF/timeline/research/network samples/Party diagnostics и сравнить одну
сцену на одинаковом устройстве. Это предложение следующего замера: настройки
в этом анализе не менялись. Ошибки GPU оставить, функциональные хуки не отключать.

## Практический порядок

1. Отделить добавленную после1.2.0 стоимость от старых handlers: замер полного
   independent tick, всех pre-event guard calls и original native HP/send/receive.
2. Заменить повторные готовые bootstrap/admission проверки и подготовку
   неизменных world/catalog/snapshot данных на revision/work-сигналы.
3. Дешёвая классификация события, локализация при init/restart; групповые
   операции по флагам с подтверждённым dirty-state вместо полного опроса.
4. Разобрать редкие scaling misses и стоимость гостевых type checks.
5. Парное1.2.0/current измерение одинаковой сцены при одинаковых диагностике,
   профилях/числе процессов, разрешении, лимите, камере, стадии загрузки и роли.
   Старую версию не устанавливать поверх живых профилей/сейвов для эксперимента.

Исследование не отключало функциональность, не откатывало версию, не меняло
настройки/сейвы/игровые файлы; сборки/деплоя/запуска в этом ходе нет.
